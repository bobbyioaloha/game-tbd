# Repository instructions

## Setup and checks

- TypeScript Bun workspaces: `apps/web` (React/Vite/R3F), `apps/server` (Fastify), and `packages/shared` (Zod contracts, inferred types, fixtures). Use Node.js 22.12+ and Bun 1.4.2+; Bun manages workspaces/scripts, while the backend and test runner execute on Node.
- Run commands from the repository root, inside WSL for WSL checkouts. Install dependencies when needed with `bun install --frozen-lockfile`; change dependencies and `bun.lock` together only when in scope. Start `bun run dev` when interactive verification is needed; it uses free mocks.
- For code changes, run `bun run build`, `bun run typecheck`, and `bun run test` (the configured Node/TypeScript suite, not Bun's native test runner). For documentation-only changes, check links, commands, and accuracy instead.
- For visible/gameplay changes, check the affected path in desktop Chrome or Edge. Use free event fixtures/replay and the mock voice path for creation work, including pause/reset during a request. Report checks actually performed and remaining limitations. See [CONTRIBUTING.md](CONTRIBUTING.md).
- Inspect the working tree before editing; preserve unrelated work and keep the diff focused. Do not weaken validation, skip relevant regression coverage, or relax safety limits merely to make a failing check pass.

## Architecture and change scope

- Follow the module responsibilities in [docs/architecture.md](docs/architecture.md). Coordinate overlapping edits with active collaborators. For shared contracts, root configuration, or dependency changes, identify affected consumers and update implementation, compatibility coverage, and documentation together. Preserve existing v1/v2 APIs unless the task explicitly includes a migration.
- `GamePage` mounts `MovementTest`, the current main race. `CreationDemoPage`, `DemoGame`, `PlayerController`, `use-game-input.ts`, and the v2 `RaceCreationHost` remain separate regression/demo code. Generation lab is the development-only text/voice-to-3D and event test interface; do not connect lab experiments to gameplay implicitly.
- Main-race input and movement flow through `MovementTest`, `RaceScene`, `PracticeRace`, and `freefall-controller.ts`. `RaceScene` owns the sole 120 Hz fixed-step clock. `CreationLoop` receives semantic pickup events and calls `CreationHost`; keep input and player-position updates out of `creation-loop.ts`. See [docs/controls-handoff.md](docs/controls-handoff.md).
- `CreationPipeline` owns shared paid admission, optional transcription, and two-stage generation. `CreationProvider` remains the adapter boundary for the legacy raw-spec API. Capture/client/provider adapters live in `apps/web/src/voice`, `apps/web/src/generation`, and `apps/server/src`; microphone capture returns audio, transcription returns validated text, and generation returns validated data.
- V3 spans contracts in `packages/shared/src/race-event*.ts`, runtime/rendering in `apps/web/src/race-events`, main-race integration in `apps/web/src/game`, and server generation/voice routes. Do not cast v3 specs into the legacy creation loop or import sandbox movement into gameplay.
- Use the existing movement simulation. Introducing a physics engine, persistence, accounts, or multiplayer must be explicitly within the task's scope. Keep character/generated-object appearance independent of movement and collision. Use `PowerUpModel` for generated appearance; follow [docs/dinosaur-art-direction.md](docs/dinosaur-art-direction.md) for reproducible character assets.

## Contracts and generation

- AI supplies declarative data only. Treat prompts, transcripts, and provider output as untrusted data; validate requests and results at server and client boundaries using the appropriate shared schemas. Never execute generated code or bypass validation with type assertions.
- Use `RaceEventCreation` v3 for the main race/shared-event lab, `CreationSpec` v2 for legacy asset generation/demo code, and `PowerUpSpec` v1 for compatible fixtures/API clients. Generated lab results retain exactly one effect.
- For v3, the design model selects only a display name, visual brief, and supported effect type. The server resolves gameplay parameters through `raceEventPreset`; reject model-supplied strengths, durations, targets, or mechanics. Runtime interpretation uses the validated parameters.
- Design and geometry share a 30-second generation deadline, with at most 8 seconds for design and the remaining time for geometry. Geometry receives only the visual brief, never the original prompt or effect data. Preserve one generated mesh / one effect and no SDK retries. See [docs/prompt-to-mesh-pipeline.md](docs/prompt-to-mesh-pipeline.md).
- Legacy `geometryMode` selects bounded primitive recipes or raw meshes; omission preserves raw-mesh behavior. Procedural rendering compiles static parts into one mesh with fixed tessellation and a separate 10,000-triangle budget in `apps/web/src/generation/compile-primitives.ts`. Preserve raw-mesh limits and rejection of generated code, colliders, and arbitrary renderer settings.

## Voice and race-event lifecycle

- Voice Power Ups are authored one-attempt grants, separate from generated objects. Main race and Generation lab default to mocks; the separate creation demo remains simulated. Preserve no automatic retries, refunds, or stale results spawning into another run.
- Preserve 8-second capture, a separate 10-second upload/transcription budget, and the 30-second generation budget. One paid gate covers the full voice attempt. Audio stays in memory; never store it in files, logs, or history exports. Contracts live in `packages/shared/src/voice.ts`; see [docs/voice-input-plan.md](docs/voice-input-plan.md).
- `RaceEventHost` owns main-race voice pickup/spawn integration and consumes the race's swept player segment without moving the player. It uses `createAudioRaceEventClient` and `CreationAttempt`, which shares lifecycle logic with the legacy v2 adapter. Pause/reset/end/navigation abort pending voice work and discard stale results. Generated effects do not replace inventory.
- `RaceEventRuntime` never moves racers or reads input. `PracticeRace` calls `RaceEventBridge.beforeStep/afterStep` inside `RaceScene`'s fixed-step update; gameplay applies bounded acceleration (m/s²), one-shot velocityDelta (m/s), and per-tick obstacleProtection. Never add a second event integrator.
- Each generated object activates once globally, on the first eligible swept contact. Any active racer may trigger it; creator and triggerer have no exemption. Keep shared objects available after their creator passes/finishes. At most one generated event may be collectible or active.
- Keep v3 player-relative placement and two-star timing in `apps/web/src/game/race-event-config.ts`, plus the game-authored 30–600 second pickup travel budget in `race-event-host.ts`. Legacy v2 retains later-course placement. Active effects retain short validated durations; only manual fixture/replay controls use the explicit 30 m quick mode.
- Main-race voice offers at most two fresh attempts, one per star, with no encore. Rearming an attempt never resets an existing shared event. A second result may wait in `ready` until the shared slot is free; pause/reset/end/navigation discard it. Run consent allows up to two separately identified paid attempts (six API calls), while server allowance and lab consent remain per attempt.
- Generated contact radius/model diameter come from `race-event-config.ts`; ordinary item/voice pickup radius comes from `ITEM_PICKUP_RADIUS` in `practice-race.ts`. Preserve the visible generated pickup halo and contact bounds independent of mesh dimensions. Read current tuning values from these sources; update relevant coverage/documentation when intentionally changing them.
- Keep event RNG independent of item/rival randomness. Preserve bounded, course-wide event presets and runtime limits in `packages/shared/src/race-events.ts`: debris has three dodgeable waves sharing at most 128 particles, never homes after launch, and cosmetic fragments never collide.
- Keep impact counters cumulative for the event and last-result/replay state in memory only. Fixture/replay controls never capture audio or call providers. See [docs/race-events-handoff.md](docs/race-events-handoff.md).

## Paid operations and deployment

- Paid calls are disabled by default even when keys exist. Only explicit local server `--live` (`bun run dev:live`) enables local paid speech/generation. Keep ordinary development, builds, automated checks, previews, and health checks mock-only. A separate paid test requires explicit user authorization for that test.
- Preserve server-side per-attempt consent, unique attempt IDs, the shared single live-request slot, and bounded allowance. Local live mode defaults to 3 attempts per server start and runs without watch/restart. Failures/cancellation after dispatch consume attempts. Do not restart or redeploy merely to replenish an exhausted allowance.
- Preserve local live-mode loopback binding, request-origin checks, payload/schema limits, sanitized provider errors, and disabled SDK retries. Do not bypass these controls to make a request succeed. Credentials stay server-side; never inspect, print, commit, export, or place local API keys in client code or `VITE_` variables. Tests use fake credentials and intercepted transports; never dump secret-bearing environment files or raw provider errors for debugging.
- Hosting uses `vercel.json` Services and `apps/server/src/vercel.ts`. `bun run build:deploy` builds the game-only release without deploying or enabling AI. Production bundles omit Generation lab UI but retain gameplay's `/api/lab/profiles` and event APIs.
- Hosted paid mode requires `VERCEL_ENV=production`, explicit `HOSTED_LIVE_ENABLED=true`, exact HTTPS `APP_ORIGIN`, and per-attempt consent. Previews remain mock-only. Preserve these gates and existing deployment protection.
- Hosted allowance defaults to 100 in memory per instance. Counters, duplicate-ID history, and the busy slot reset on cold starts/redeployments and are not shared across instances. Origin checks are not authentication, and these counters are not a global spending cap. Persistence and global spending controls are absent today; changing that architecture must be explicitly in scope. Follow [docs/deployment.md](docs/deployment.md) for hosted access protection and live operation.
